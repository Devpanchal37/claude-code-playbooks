# Chapter 18: Team Collaboration

> **Applies to:** Both
> **Prerequisites:** Chapter 4: CLAUDE.md File, Chapter 8: Agent Creation Guide, Chapter 12: Auto-Memory System
> **Estimated read + setup time:** ~20 minutes

---

## TL;DR

Committing the wrong files breaks team collaboration in two directions: too little committed means every developer rebuilds the setup from scratch; too much committed means personal preferences, local API keys, and per-developer memory entries overwrite each other. This chapter defines exactly what goes into git, what stays local, how a new team member gets set up in one session, and how to prevent two developers from breaking the orchestra by editing it simultaneously.

---

## What This Is

The Claude Code agentic setup spans two locations: the project repository (`.claude/` and `docs/`) and the developer's local machine (`~/.claude/`). Team collaboration works when the project-level setup is shared via git and the personal setup stays local.

There is also a third location that teams often miss: the Claude Mem MCP database. By default it is per-installation — one developer's observations are invisible to another developer's agents. This chapter covers how to handle all three locations correctly.

---

## Why It Exists (The Problem It Solves)

**Without a clear commit policy:**

- Developer A commits their auto-memory files. Developer B pulls and their agents start using Developer A's personal preferences as if they were project rules.
- Developer A updates `agents.md` for a new agent. Developer B updates `agents.md` for a different trigger. Both push on the same day — merge conflict in the orchestra file, which neither developer fully understands.
- A new developer joins the project. They clone the repo, have no idea which files belong in `.claude/`, and spend two sessions reconstructing what the team built over two months.

**With this protocol:** New developers clone the repo, run two setup commands, and have a working agentic environment in under 30 minutes. Orchestra conflicts are rare because one person owns the file. Auto-memory stays personal.

## What to Commit

These files are shared across the entire team. Every developer gets them on `git pull`.

### Project-level `.claude/` directory

```
.claude/
  agents/          ← COMMIT — all agent files, shared conventions
  rules/           ← COMMIT — coding standards, git workflow, security rules
  settings.json    ← COMMIT — project permissions (without personal API keys)
```

**Why each is shared:**
- `agents/`: agents encode project conventions. Every developer must have the same developer agent, the same systematic-debugger, the same code-reviewer. Divergent agent files mean different developers enforce different rules.
- `rules/`: coding standards, commit message format, security checklists — these are project-level contracts, not personal preferences.
- `settings.json`: the project-level allowed tools list and hook registrations. Without this, every developer must manually approve routine tool calls that the team has already decided are safe.

### `CLAUDE.md`

Always committed. This is the session start file that every developer's Main Claude reads. It defines the identity of the setup — who Claude is on this project, which critical rules apply, which triggers fire which agents.

### `docs/` folder

The entire `docs/` folder is committed. This includes:

```
docs/
  FR/              ← COMMIT — requirements and pipeline status
  instructions/    ← COMMIT — architecture, UI, and API instruction files
  maps/            ← COMMIT — project map (regenerated by agent)
  memory/          ← COMMIT — error learnings, component registry, API registry
  backend_issues/  ← COMMIT — backend bug log maintained by systematic-debugger
```

The `docs/memory/` files are intentionally shared. `error_learnings.md` is the most important file to share — when Developer A discovers a non-obvious mistake, every developer's agents benefit from that learning immediately on next pull.

> **NOTE:** `docs/maps/project_map.md` is regenerated by the project-map agent. Treat merge conflicts in this file as auto-resolved — always use the most recently generated version, not a manual merge.

## What NOT to Commit

These files are per-developer. Committing them causes subtle, hard-to-diagnose conflicts.

### Auto-memory files

```
.claude/projects/[project-hash]/memory/   ← NEVER COMMIT
```

Auto-memory stores personal preferences, feedback about your own work style, and user-role context. If Developer A's auto-memory notes "this developer prefers short commit messages," Developer B should not have that preference applied to their sessions.

Add this to `.gitignore`:

```gitignore
# Claude Code auto-memory (per-developer, not shared)
.claude/projects/
```

### User-level settings

```
~/.claude/settings.json   ← NEVER COMMIT (it's outside the repo anyway)
```

User-level settings include personal model preferences, personal allowed tools beyond the project list, and potentially API keys. These never belong in a project repository.

### Files with API keys or tokens

Any file containing `ANTHROPIC_API_KEY`, tokens, or credentials must not be committed, even temporarily. The project `settings.json` should reference environment variables, not contain actual values:

```json
{
  "env": {
    "MY_APP_API_URL": "${MY_APP_API_URL}"
  }
}
```

### Session-specific files

Anything Claude Code creates during a session that is specific to a single conversation — temporary analysis files, mid-session notes written to the repo root — should be cleaned up before committing.

### Complete `.gitignore` additions

Add these entries to the project's `.gitignore`:

```gitignore
# Claude Code — per-developer, never shared
.claude/projects/

# Claude Code — session artifacts (if any land in project root)
.claude/.session*
```

## Onboarding a New Team Member

A new developer joins the project. They clone the repo. Here is the complete sequence to get their agentic environment working.

### Step 1 — Clone the repository

```bash
git clone [repository-url]
cd [project-directory]
```

The `.claude/` directory and `docs/` folder are now present — they came in with the clone.

### Step 2 — Install Claude Code CLI

Follow the official Claude Code installation guide. The CLI must be installed and authenticated before the setup works.

### Step 3 — Install the Claude Mem MCP plugin

The Claude Mem MCP is not in the repository — it is installed per-developer. Run:

```bash
claude mcp add claude-mem
```

Verify it appears in the MCP list:

```bash
claude mcp list
```

Without this step, every agent's Pre-Step will fail silently — the `smart_search` tool calls return nothing, and agents proceed without historical context.

### Step 4 — Set project environment variables

Check `CLAUDE.md` and `.claude/settings.json` for required environment variables. Set them in the developer's local environment. Do not put actual values in any committed file.

### Step 5 — Run the first validation

Open Claude Code in the project directory. Send:

```
What is the current pipeline status?
```

Main Claude should read `docs/FR/_pipeline_status.md` and report the current task state. If it responds with a general answer instead of reading the file, the session start protocol in `CLAUDE.md` is not being applied — check that `CLAUDE.md` is present at the project root.

### Step 6 — Trigger one agent manually

Send:

```
develop [any module name that has an existing FR plan]
```

Verify the developer agent launches and reads its instruction files. The new developer is now operational.

## Handling Personal Customizations

Sometimes a developer needs agent behavior that diverges from the team default — a different working style, a personal shortcut, or an experimental agent variant.

**The rule:** Base agent files in `.claude/agents/` are shared and committed. Personal customizations stay in a local-only override that is gitignored.

### Creating a personal agent override

1. Create a local override directory:
   ```
   .claude/agents-local/   ← gitignored, per-developer
   ```

2. Add to `.gitignore`:
   ```gitignore
   .claude/agents-local/
   ```

3. Create the override agent file at `.claude/agents-local/developer.md` — this file has the same name as the base agent but different instructions.

4. In your personal Claude Code settings, configure the local agents directory to take precedence over the shared one.

> **WARNING:** Personal overrides diverge silently. A developer using a custom developer agent may generate code that passes their local code-reviewer but fails the team's shared code-reviewer when another developer runs it.  
> Instead: propose the change to the shared agent file. If it is genuinely personal, use a personal-override with a distinct name (e.g., `developer-relaxed.md`) so the override is visible in the trigger.

## Shared Claude Mem MCP

By default, each developer's Claude Mem MCP database is per-installation. Developer A's error learnings stored in claude-mem are invisible to Developer B's agents.

This is a trade-off: per-installation means no accidental overwriting of each other's observations. But it also means each developer's agents re-discover the same non-obvious patterns independently.

### Option 1 — Accept per-installation (default, recommended for small teams)

Compensate with the shared `docs/memory/error_learnings.md`. Every significant discovery that an agent stores to claude-mem should also be written to `error_learnings.md` in the format:

```
## [YYYY-MM-DD] Short Title
**Mistake/Issue:** what went wrong
**Correct:** what should be done instead
**Pattern:** the general rule going forward
```

This file is committed and shared. Every developer's agents read it during their Pre-Step. The discovery propagates to the whole team on the next `git pull`.

### Option 2 — Shared claude-mem server (advanced, larger teams)

Configure the Claude Mem MCP to point to a shared server or shared database file that all developers access. The configuration goes in each developer's `~/.claude/settings.json` (not the project settings):

```json
{
  "mcpServers": {
    "claude-mem": {
      "command": "claude-mem",
      "args": ["--database", "/shared-network-path/project-memory.db"]
    }
  }
}
```

> **WARNING:** A shared database means all developers write to the same store. One developer storing a personal preference ("this developer prefers verbose commit messages") becomes visible to all agents across the team.  
> Instead: when using a shared database, agents should only store project-level knowledge (discovered patterns, confirmed root causes, architecture decisions) — never user-level preferences.

## Orchestra Ownership (Merge Conflict Prevention)

`agents.md` (the orchestra file at `.claude/rules/common/agents.md`) is the most conflict-prone file in the setup. It defines trigger tables and quality tier rules that multiple developers may want to update simultaneously.

### The single-owner rule

Assign one developer as the **orchestra owner**. This role rotates with the tech lead or is assigned to the most senior developer.

- Only the orchestra owner commits changes to `agents.md`
- Other developers submit proposed changes as pull requests with a clear description of: which trigger they are adding, which agent it fires, and why
- The orchestra owner reviews, merges, and communicates the change to the team

This is not bureaucracy — it is protection. Two developers updating the same trigger table on the same day creates a merge conflict in a file where a wrong merge silently breaks all agent routing.

### When a developer needs an urgent orchestra change

If a developer needs a trigger change and the orchestra owner is unavailable:

1. Make the change in a dedicated branch named `orchestra/[change-description]`
2. Leave a comment in `agents.md` at the changed line: `# PENDING REVIEW — [developer initials] [date]`
3. Ping the orchestra owner before merging — do not auto-merge orchestration changes

### Resolving a merge conflict in `agents.md`

When a conflict does occur:

1. Do not use "accept theirs" or "accept mine" blindly — both changes may be valid
2. Read both versions of the conflicted section
3. Manually merge the two trigger entries — one does not override the other
4. Test both triggers after resolving: send the exact trigger message for each changed entry and verify the correct agent fires

## Validation

### Validation Test 1: New developer setup works end-to-end

**Purpose:** Verify a developer cloned the repo can trigger an agent without any manual configuration beyond the two install steps.

**Setup:** Have a colleague (or use a second machine) clone the repo fresh. They complete Steps 1–6 from the Onboarding section.

**Trigger:**
```
What is the current pipeline status?
```

**Expected result:** Main Claude reads `docs/FR/_pipeline_status.md` and reports the current task state, not a generic answer.

**If it doesn't work:** Verify `CLAUDE.md` is in the repo root and the session start protocol in it explicitly references `docs/FR/_pipeline_status.md` as Tier 1 reading.

---

### Validation Test 2: Auto-memory stays local

**Purpose:** Verify that auto-memory files are not tracked by git.

**Trigger:**
```bash
git status
git ls-files --others --exclude-standard | grep ".claude/projects"
```

**Expected result:** No `.claude/projects/` files appear in `git status` (tracked or untracked). The `grep` returns nothing.

**If auto-memory appears in git status:** The `.gitignore` entry is missing or malformed. Add `.claude/projects/` to `.gitignore` and verify with `git check-ignore -v .claude/projects/[any-file]`.

---

### Validation Test 3: Agent files are shared correctly

**Purpose:** Verify all agent files are committed and present for a new developer.

**Trigger:**
```bash
git ls-files .claude/agents/
```

**Expected result:** All agent files appear — developer.md, systematic-debugger.md, planner.md, code-reviewer.md, and any others the team uses.

**If an agent is missing:** It was created locally but never committed. Add it with `git add .claude/agents/[agent-name].md` and commit.

## Common Mistakes

### Mistake 1: Committing `.claude/projects/` auto-memory

**Symptom:** After a pull, agents start using another developer's personal preferences. Session start loads memory entries referencing work, tools, or preferences that don't match the current developer's context.

**Cause:** `.claude/projects/` was committed either directly or by a `git add .` that swept in everything under `.claude/`.

**Fix:** Add `.claude/projects/` to `.gitignore`. Remove it from tracking: `git rm -r --cached .claude/projects/`. Commit the `.gitignore` update.

---

### Mistake 2: Not committing `docs/memory/error_learnings.md`

**Symptom:** Developer B's agents repeat a mistake that Developer A's agents discovered and solved last sprint. The team's agents are not learning from shared experience.

**Cause:** `docs/memory/` was partially gitignored, or the developer who made the discovery forgot to commit the updated file.

**Fix:** Confirm `docs/memory/error_learnings.md` is tracked: `git ls-files docs/memory/`. If not tracked, `git add docs/memory/error_learnings.md`. Add a team norm: any time an agent writes to `error_learnings.md`, the developer commits it before end of day.

---

### Mistake 3: Two developers updating `agents.md` at the same time

**Symptom:** Merge conflict in `agents.md`. One developer's trigger entry is overwritten. An agent that was working last week silently stops firing.

**Cause:** No orchestra ownership was established. Both developers edited `agents.md` in their branches and the auto-merge was wrong.

**Fix:** Assign an orchestra owner immediately. Resolve the conflict manually (read both versions, merge both entries). Re-validate both changed triggers using the exact trigger messages.

---

### Mistake 4: New developer skips Claude Mem MCP install

**Symptom:** The developer agent's Pre-Step runs but produces no memory results. Agents re-discover mistakes already in the team's shared knowledge. No error is shown — the MCP call silently returns empty.

**Cause:** Claude Mem MCP is not installed per-developer. It is not in the repository — each developer must install it.

**Fix:** Add a `SETUP.md` or similar onboarding document to the repository root that lists the two required installs: Claude Code CLI and `claude mcp add claude-mem`. The Onboarding section in this chapter can be adapted for that document.

---

### Mistake 5: Personal agent override diverges silently

**Symptom:** A developer reports "it worked on my machine." Their locally-customized developer agent generates code the team's code-reviewer doesn't recognize as compliant.

**Cause:** The developer created a personal override of the developer agent with relaxed widget placement gate rules.

**Fix:** Delete the personal override. Reproduce the issue with the shared agent. If the shared agent needs to change, propose the change via pull request to the orchestra owner.
